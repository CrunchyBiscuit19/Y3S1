## Overview

`asdf.cpp` is a short C++ program that randomly generates `ARRAY_SIZE` integers (`int`) from `[0, MAX_VALUE)` into a vector (`std::vector`), then sorts the vector in ascending order. It also prints out the last 5 elements of this sorted array.  

The sorting function `my_sort` used implements the bubble sort algorithm, which performs $O(n^2)$ comparisons over the vector to sort it in ascending order, where $n$ is the size of the array.  

With the bubble sort algorithm, it does `ARRAY_SIZE - 1` passes of the array, sorting adjacent elements of the array in-place until every element is correctly sorted.

## Execution

Between `ARRAY_SIZE` and `MAX_VALUE`, `ARRAY_SIZE` would have a greater effect on the performance when it is increased, since it increases the work the program has to do, while `MAX_VALUE` only changes the values being sorted, not the amount of work done.  As such, this report will focus on how changes to `ARRAY_SIZE` affect the program.

A duplicate of the `asdf.cpp` program, `slow_asdf.cpp` was compiled with the `g++` compiler as `g++ slow_asdf.cpp -O0 -o slow_asdf`. Only minor changes were made to accept a command line input for the array size. Compilation optimizations were disabled to prevent complications with profiling analysis.

`slow_asdf` was compiled with `ARRAY_SIZE` $\in$  `{1e4, 2e4, 4e4, 6e4, 8e4, 1e5}`. This progressive increase in `ARRAY_SIZE` creates a large enough difference in performance to be observable when analysing the data.

This graph was created with data collected using `perf` running on the `xs-4114, i7-7700, i7-13700` partition on the Slurm clusters to ensure that results are consistent across different hardware. All versions of `slow_asdf` with different `ARRAY_SIZE` are run 5 times on a node of each partition, with error bars displaying the difference between the best and worst runs.

From the graphs above, the metrics do not all scale at the same rate. Execution time, instruction count, CPU cycles, and branch misses all scale quadratically with `ARRAY_SIZE` as expected due to the $O(n^2)$ comparisons that must be made in a bubble sort. Cache references and misses grow only linearly since bubble sort streams over the same $O(n)$-element working set on every pass, so cache traffic is not affected to the same degree by the $O(n^2)$ comparisons as other metrics.

## Optimization

 A modified version of the `asdf.cpp` program, `fast_asdf.cpp` was compiled with the `g++` compiler as `g++ fast_asdf.cpp -O0 -o fast_asdf` for the same reasons stated earlier.

The optimization that was made to `fast_asdf.cpp` is to replace the `my_sort` function with a `fast_sort` function, which simply calls `std::sort` on the randomly-generated vector in the code. On `g++`, `std::sort` is implemented as the hybrid-sorting algorithm introsort, which performs $O(n \log n)$ comparisons in the worst case, which means it should also decrease the number of instructions needed.

As before, `fast_asdf` was compiled with `ARRAY_SIZE` $\in$  `{1e4, 2e4, 4e4, 6e4, 8e4, 1e5}`, and run on `xs-4114, i7-7700, i7-13700` partition on the Slurm clusters, with 5 runs each for every value of `ARRAY_SIZE` and a node of each partition.

![[fast_task_clock_msec.png|427]] ![[fast_instructions.png|427]] ![[fast_cycles.png|427]] ![[fast_branch_misses.png|427]] ![[fast_cache_misses.png|427]] ![[fast_cache_references.png|427]]

From the graphs above, it can be seen that the change in the sorting function has resulted in lower execution time, instruction counts, CPU cycles, branch misses, cache misses, and cache references. The growth of these figures across increasing `ARRAY_SIZE` has more of a linear curve compared to that of `slow_asdf`, which demonstrates its increasing effectiveness in optimizing the program for larger `ARRAY_SIZE`.

Since `fast_asdf` uses introsort, the quick-sort algorithm would be employed for arrays of these sizes. Introsort performs only $O(n \log n)$ comparisons rather than $O(n^2)$, the effect of which compounds as `ARRAY_SIZE` grows. The far lower comparison count directly lowers the instruction count, and with it the CPU cycles, execution time, and branch misses. The comparisons also touch a much smaller effective working set, which keeps cache references and misses low. Unlike the `slow_asdf` bubble sort, none of these metrics grows quadratically with `ARRAY_SIZE`, which is why the gap between the two versions of `asdf` widens for larger arrays.

As with `slow_asdf`, L1 / L2 / LLC breakdown with `xs-4114, i7-7700, i7-13700` node types will be included in the appendix.

And by analyzing the generated flamegraph from the first run of `fast_asdf` with `ARRAY_SIZE=1e5` on an `i7-13700` node (same conditions as the previous flamegraph), we can tell that the new `fast_sort` function takes up less of the total execution time in `main` as compared to `my_sort` , such that the unchanged `generateLargeArray` function takes up proportionally more space than in `slow_asdf`.

The results are collected by running a script `bench.sh` with `sbatch` on 1 node each of the `xs-4114, i7-7700, i7-13700` of the CS3210 PDC lab cluster.
The nodes used for `xs-4114, i7-7700, i7-13700` are `soctf-pdc-001`, `soctf-pdc-009`, and `soctf-pdc-033` respectively.

```sh
#!/bin/bash
#SBATCH --job-name=asdf_bench
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --exclusive
#SBATCH --time=01:00:00
#SBATCH --output=bench_%j.log
#SBATCH --error=bench_%j.log

PART="${SLURM_JOB_PARTITION:?submit with a partition, e.g. sbatch -p xs-4114 bench.sh}"
EVENTS=task-clock,cycles,instructions,branch-misses,cache-references,cache-misses
HEADER="bin,size,run,task_clock_msec,cycles,instructions,branch_misses,cache_references,cache_misses,L1-dcache-loads,L1-dcache-load-misses,l2_rqsts.references,l2_rqsts.miss,LLC-loads,LLC-load-misses"
BINARIES="slow_asdf fast_asdf"
SIZES="1 2 4 6 8 10"
RUNS=5

csv="runs_${PART}.csv"
echo "$HEADER" > "$csv"
for bin in $BINARIES; do
  for size in $SIZES; do
    for run in $(seq 1 $RUNS); do
      for attempt in 1 2 3; do
        out=$(srun perf stat -x, -e "$EVENTS" "./$bin" "$size" 2>&1 >/dev/null)
        vals=$(echo "$out" | awk -F, -v ev="$EVENTS" '
          BEGIN{n=split(ev,a,",")}
          $3!=""{e=$3; sub(/^cpu_[a-z]+\//,"",e); sub(/\/$/,"",e);
                 if(!(e in v) || (v[e] ~ /[^0-9.]/ && $1 ~ /^[0-9.]+$/)) v[e]=$1}
          END{for(i=1;i<=n;i++){x=(a[i] in v)?v[a[i]]:"NA"; if(x ~ /[^0-9.]/)x="NA"; printf "%s%s", (i>1?",":""), x}}')
        case "$vals" in *NA*) continue;; esac
        break
      done
      echo "${bin},${size},${run},${vals}" >> "$csv"
    done
    awk -F, -v b="$bin" -v sz="$size" 'NR>1 && $1==b && $2==sz{for(i=4;i<=NF;i++)s[i]+=$i;n++;c=NF} END{printf "%s,%s,avg",b,sz; for(i=4;i<=c;i++)printf ",%.2f",s[i]/n; print ""}' "$csv" >> "$csv"
  done
  srun bash -c 'd="flame_'"$bin"'_'"$PART"'"; mkdir -p "$d"; cd "$d"; flamegraph -- "../'"$bin"'" 10'
done
echo "Done on $PART. Collect runs_${PART}.csv and flame_*_*/flamegraph.svg"
```

For each binary, the script tests it for each size argument (`SIZES="1 2 4 6 8 10"`, corresponding to `ARRAY_SIZE` $\in$  `{1e4, 2e4, 4e4, 6e4, 8e4, 1e5}`), via 5 runs of `perf` (in `perf stat -x, -e "$EVENTS" "./$bin" "$size" 2>&1 >/dev/null`) for 5 data points each. 
The results of these runs are parsed and written into a CSV file, which is then `scp`'d into my local machine. The Python script `plot.py` is run using this CSV file to generate the graphs in this report.

```python
import csv
import math
import re
from pathlib import Path
import matplotlib
matplotlib.use("Agg")
import matplotlib.pyplot as plt
import numpy as np
import pandas as pd

BASE = Path(__file__).resolve().parent / "T01"
OUT_CSV = Path(__file__).resolve().parent / "all_runs.csv"
PLOT_DIR = Path(__file__).resolve().parent / "plots"

HARDWARE = ["xs-4114", "i7-7700", "i7-13700"]
HW_COLORS = {"xs-4114": "#1f77b4", "i7-7700": "#ff7f0e", "i7-13700": "#2ca02c"}

ELEMS_PER_UNIT = 10000
BYTES_PER_ELEM = 4
L2_SIZES = {
    "xs-4114": 1 * 1024 * 1024,
    "i7-7700": 256 * 1024,
    "i7-13700": 2 * 1024 * 1024,
}
CANON = ["task_clock_msec", "cycles", "instructions", "branch_misses",
         "cache_references", "cache_misses",
         "l1_dcache_loads", "l1_dcache_load_misses",
         "l2_references", "l2_misses",
         "llc_loads", "llc_load_misses"]
METRICS = ["task_clock_msec", "cycles", "instructions",
           "branch_misses", "cache_references", "cache_misses"]
METRIC_LABELS = {
    "task_clock_msec": "Task clock (ms)", "cycles": "CPU cycles",
    "instructions": "Instructions", "branch_misses": "Branch misses",
    "cache_references": "Cache references", "cache_misses": "Cache misses",
}

KEY_COLS = ("bin", "size", "run")
BASE_RE = re.compile(r"^runs_(?!cache_)(.+)\.csv$")
CACHE_RE = re.compile(r"^runs_cache_(.+)\.csv$")

def convert_num(x: str) -> float:
    try:
        return float(x)
    except (TypeError, ValueError):
        return math.nan

def read_runs(path: Path, hardware: str):
    with path.open(newline="") as f:
        reader = csv.reader(f)
        header = next(reader, None)
        if not header:
            return
        header = [h.strip() for h in header]
        for fields in reader:
            if not fields:
                continue
            row = dict(zip(header, [x.strip() for x in fields]))
            if row.get("run", "").lower() == "avg":
                continue
            try:
                size = int(row["size"])
                run = int(row["run"])
            except (KeyError, ValueError):
                continue
            rec = {
                "binary": row["bin"].replace("_asdf", ""),
                "hardware": hardware,
                "size": size,
                "array_size": size * ELEMS_PER_UNIT,
                "run": run,
            }
            for col, val in row.items():
                if col not in KEY_COLS:
                    rec[col] = convert_num(val)
            yield rec

def consolidate() -> pd.DataFrame:
    records = []
    for csv_path in sorted(BASE.glob("runs_*.csv")):
        m = CACHE_RE.match(csv_path.name) or BASE_RE.match(csv_path.name)
        if not m:
            continue
        hardware = m.group(1)
        records.extend(read_runs(csv_path, hardware))
    df = pd.DataFrame.from_records(records)
    id_cols = ["binary", "hardware", "size", "array_size", "run"]
    metric_cols = ([c for c in CANON if c in df.columns]
                   + [c for c in df.columns if c not in CANON and c not in id_cols])
    df = df[id_cols + metric_cols]
    df = df.sort_values(
        ["binary", "hardware", "array_size", "run"]).reset_index(drop=True)
    df.to_csv(OUT_CSV, index=False)
    print(f"Wrote {len(df)} rows, columns={metric_cols} -> {OUT_CSV}")
    return df

def usable(df: pd.DataFrame, *cols) -> bool:
    return all(c in df.columns for c in cols) and \
        bool(df[list(cols)].notna().all(axis=1).any())
  
def plot_cache_levels(df: pd.DataFrame):
    PLOT_DIR.mkdir(exist_ok=True)
    df = df.copy()
    plots = []  
    if usable(df, "l1_dcache_load_misses", "l1_dcache_loads"):
        df["l1_miss_rate"] = df["l1_dcache_load_misses"] / df["l1_dcache_loads"]
        plots.append(("l1_miss_rate", "L1D load miss rate", False))
    if usable(df, "l2_misses", "l2_references"):
        df["l2_miss_rate"] = df["l2_misses"] / df["l2_references"]
        plots.append(("l2_miss_rate", "L2 miss rate", False))
        plots.append(("l2_misses", "L2 misses (count)", True))
    if usable(df, "llc_load_misses", "llc_loads"):
        df["llc_miss_rate"] = df["llc_load_misses"] / df["llc_loads"]
        plots.append(("llc_miss_rate", "LLC load miss rate", False))
    made = []
    for binary in sorted(df["binary"].unique()):
        bdf = df[df["binary"] == binary]
        for col, label, log_y in plots:
            if col not in bdf or bdf[col].notna().sum() == 0:
                continue
            agg = bdf.groupby(["hardware", "array_size"])[col].agg(["mean", "std"])
            xs = np.sort(bdf["array_size"].unique())
            fig, ax = plt.subplots(figsize=(7, 4.5))
            for hw in HARDWARE:
                if hw not in agg.index.get_level_values(0):
                    continue
                s = agg.loc[hw]
                ax.errorbar(s.index.values, s["mean"].values,
                            yerr=np.nan_to_num(s["std"].values),
                            marker="o", capsize=3, color=HW_COLORS.get(hw), label=hw)
                if hw in L2_SIZES:
                    l2_elems = L2_SIZES[hw] / BYTES_PER_ELEM
                    if xs.min() <= l2_elems <= xs.max():
                        ax.axvline(l2_elems, color=HW_COLORS.get(hw),
                                   ls="--", alpha=0.4)
            ax.set_xlim(xs.min(), xs.max())
            if log_y:
                ax.set_yscale("log")
            ax.set_title(f"{label} vs array size ({binary}_asdf)")
            ax.set_xlabel("Array size (elements)")
            ax.set_ylabel(label)
            ax.grid(True, which="both", ls=":", alpha=0.6)
            ax.legend(title="Hardware (dashed = its L2 size)")
            fig.tight_layout()
            out = PLOT_DIR / f"{binary}_{col}_vs_elements.png"
            fig.savefig(out, dpi=150)
            plt.close(fig)
            made.append(out.name)
            print(f"ploted {out.name}")
    return made

def plot(df: pd.DataFrame):
    PLOT_DIR.mkdir(exist_ok=True)
    present = [m for m in METRICS if m in df.columns]
    agg = df.groupby(["binary", "hardware", "array_size"])[present].agg(["mean", "std"])

            ax.grid(True, which="both", ls=":", alpha=0.6)
            ax.legend(title="Hardware")
            fig.tight_layout()
            out = PLOT_DIR / f"{binary}_{metric}.png"
            fig.savefig(out, dpi=150)
            plt.close(fig)
            made.append(out.name)
            print(f"ploted {out.name}")
    return made

if __name__ == "__main__":
    df = consolidate()
    base = plot(df)
    cache = plot_cache_levels(df)
```

### `i7-7700` Cache Behaviour

The `i7-7700` outlier is explained by its private L2 cache being much smaller than the other two nodes. Per Intel, the Core i7-7700 (Kaby Lake) has a **256 KB** L2 cache per core (on top of a 32 KB L1 data cache per core and an 8 MB shared L3), whereas the `xs-4114` (Xeon Silver 4114) has a **1 MB** private L2 per core and the `i7-13700` (Raptor Lake) has a **2 MB** private L2 per P-core.

A `256 KB` L2 holds only `256 KB / 4 B = 65,536` `int` elements. Once `ARRAY_SIZE` grows past this point (the dashed orange marker in the L2 graphs), the working set no longer fits in the `i7-7700`'s L2 and every pass must fetch from the shared L3, so its L2 miss rate climbs steeply. The larger `1 MB` and `2 MB` L2 caches keep the entire array (at most `1e5` elements `= 400 KB`) resident across all tested sizes, so their L2 miss rates stay flat. The L1 and LLC breakdowns behave near-identically across all three nodes, confirming that the L2 capacity is the sole cause of the divergence.
